## 1. 작업 배경 및 문제 분석

직전 작업에서는 원문 근거의 말끝 변환, 동일 관계 근거 누락, 엄격 수치 경계와 중복 제외를 보완했다. 당시 최종 8문항은 피드백 노출 회귀였으며 전체 자연어 지원 완료의 근거가 아니다. 이번에는 문장 하나의 성공과 질문군에서 유지되는 동작을 구분한다.

선행 기록에서 한국명 “비둘기과”의 실제 이름 조회 실패는 남았다. 학명 `Columbidae`의 별도 성공은 한국명 성공으로 계산하지 않는다. 자료 부재와 질문 해석 오류도 별개로 보고한다.

## 2. 해결 방안 및 설계

기존 검색·해석·검증·조회 사이의 경계를 유지하고, 질문을 확인해야 할 때 원문 조건을 짚도록 변경했다. 새 대화 저장 계층이나 새 자동 학습 파이프라인을 만드는 대신 기존 계약을 재사용했다.

```text
현재 질문 → 검증된 유사 예시 검색 → 현재 원문의 조건 추출·검증
          → 불확실한 조건 구체적 확인 → 확인된 조건으로 그래프 조회
```

- 예시는 해석의 참고 자료로 사용하고 종·분류군·먹이·서식지·수치·부정 조건은 현재 원문에서 검증한다.
- 기존 되묻기·후보 선택·조회 계약을 재사용한 범위와 새로 추가한 범위를 구분한다.
- 예시가 부족하거나 조건을 확인할 수 없을 때의 실제 응답 및 그래프 실행 여부를 기록한다.
- 특정 식물 먹이 자료, 부정·미지원 조건, 이름 자료 한계를 임의 완화하지 않는지 확인한다.
- 모델 감사·원문 검증을 통과한 사실과 실제 API·자료 조회 성공을 따로 기록한다.

- `src/robingraph/generation.py` — `GeminiAnswerError`에 reason과 original_spans를 보존한다. 감사 거절을 전송 장애와 구분할 수 있도록 기존 예외 경로에서 근거를 전달한다.
- `src/robingraph/api/services.py` — 실제 원문과 일치하는 최대 3개 구간을 인용하고 인접 구간은 합친다. 미지원 관계·제외 조건·미해결 구간·분류명 모호성·비교 기준 종 부재별로 구체적 확인을 요청한다. 감사 거절과 일시적 해석 장애의 안내를 구분한다.

- `src/robingraph/retrieval/graph_condition_extractor.py` — “되/하” 계열 연결 어미를 식물명으로 오인하는 lexical 경계를 보완한다.
- `scripts/evaluate_graph_question_families.py` — 개별 실행 계획, 동치 문항 일치, 대조 문항 차이, 질문군 전체 통과를 각각 판정한다.
- `data/eval/graph_questions/question-families-v1/` — 공개 tuning·manifest·validation. 봉인 문항 본문은 문서 작성자가 열지 않았다.

### 최초 봉인 실패 이후의 보완

요청 말끝은 기존 `_ASKS` 전체 일치와 제한된 종결어 패턴을 모두 만족하고, 원문에서 유일하게 확인되는 마지막 독립 구간일 때만 정규화한다. 조건을 가진 구절을 요청 표현으로 삭제하지 않는다. 자체 제외 표현은 `_REMOVE`의 쉼표 경계를 보완했다. 의도하지 않은 `_named_taxa` 변경은 최종 범위에서 되돌렸으므로 분류명 검출 개선으로 기록하지 않는다.

독립 followup 5건은 `request-self-final.log`에 통과로 기록됐고 수정 전 2건 실패는 `request-self-before.log`에 보존했다. 원래 봉인 파일을 덮어쓰지 않고 `regression.json`에 `implementation_feedback_exposed: true`인 별도 재검증 자료를 둔다. 첫 실제 24문항 재검증의 실패와 마지막 후보의 결과는 별도 표로 구분한다.

### 변경 전후와 범위

이전에는 검색한 예시 중 정형 계획이 없는 항목도 참고 목록으로 들어갈 수 있었다. 이제 고정된 계획 13개 중 현재 계약을 통과한 예시만 검색 대상으로 삼고 반환 행도 같은 풀과 대조한다. 여기서 “검증”은 로컬 실행 계약 검사이며 모든 예시가 실제 DB 응답이나 사람 검토를 받았다는 의미가 아니다.

이전에는 서로 다른 실패 원인에도 비교 기준 또는 재입력을 포괄적으로 요구했다. 이제 원문에서 확인한 구간과 조건별 한계를 설명하며, 모델 설명을 그대로 사용자에게 인용하지 않는다. `semantic_audit_rejected`가 아닌 전송·제공자 장애는 일시적 장애 안내를 유지한다.

```text
계약 검사된 고정 예시 풀 → 기존 임베딩 검색 → 일치하는 예시 최대 5개
현재 원문 → 계획·감사·검증 → 구체적 확인 또는 고정 그래프 조회
실행 가능한 계획 → trace의 canonical_plan → 질문군 평가
```

자동 학습·답변 캐시·질문 노드 자동 적재·자유 Cypher 생성·계약 스키마 확장을 추가하지 않았다. “되묻기” 안내를 추가한 사실과 선택·후속 입력이 전체 대화 흐름에서 재개된다는 검증은 구분한다. 이번 검증은 개별 요청·같은 요청 trace의 해석/조회/되묻기 응답을 확인한 범위다. 브라우저에서 사용자가 되묻기에 답한 뒤 이어지는 다중 턴 흐름을 새로 검증했다고 주장하지 않는다.

## 4. 검증 및 테스트 결과

### 로컬 검사

전체 검사는 `python -m unittest discover -s tests -v`로 실행한 Python 회귀이며 의존성과 실행 옵션은 Codex의 검증 환경을 사용했다. 평가 스크립트는 `--cases`, `--responses`, `--catalog`, `--out`으로 문항·동일 요청 응답·분류 catalog·점수 파일을 명시한다.

초기 직접 호출에서는 tests 경로가 빠져 `asgi_client` import 오류 2건이 났고 `PYTHONPATH=tests:src`로 정정했다. 이후 모의 감사 안내 검사 1건, 초기 전체 1,280 실행에서 SDK 조건에 따라 드러난 감사 안내 검사 5건이 실패했다. SDK의 관측 상태를 응답 분기 근거로 사용하지 않고 예외의 `error.reason`만 확인하도록 수정했다. 감사 거절을 단순 장애로 분류하던 경로를 `error.reason`에 따라 구분한 뒤 중간 전체 1,280 실행 중 1,240 통과·40 skip·0 실패(23.497초)를 확인했다. 초기 실패는 `unit-initial.log`에 보존했다. 봉인 실패 보완 후 중간 전체 결과는 1,285 실행·1,245 통과·40 skip·0 실패(23.433초)였다. 이어진 실제 회귀 실패 보완까지 포함한 최종 전체 결과는 1,286 실행·1,246 통과·40 skip·0 실패(24.078초)이며 `unit-full.log`에 저장했다. graphify 갱신 결과는 8,536 nodes·18,707 edges·465 communities다. 실제 서버·모델 결과와 이 로컬 검사를 혼합하지 않는다.

### 첫 실제 TEST 결과

| 평가 | 판정 통과 | 질문군 통과 | 실제 결과와 한계 |
| --- | --- | --- | --- |
| 공개 tuning | 6/6 | 2/2 | 봉인 평가와 분리 |
| 최초 봉인 holdout | 16/18 | 4/6 | false hold 2건을 원래 결과에 보존 |

최초 봉인 18문항의 실제 응답은 지원 답변 14건, 지원 범위이나 직접 자료가 없는 H05A 1건, 부정 조건 보류 H04C 1건, false hold H05B·H06B 2건이다. H05A는 아종의 직접 자료가 없어 `supported_source_no_data`로 분리한다. 부모 종 자료로 대체하지 않았으며, 16개 판정 통과를 16개 답변 성공이라고 표현하지 않는다.

H05B는 요청 말끝 “궁금해”, H06B는 기준 종 자체 제외 표현 “빼고,”의 구두점 처리 때문에 false hold였다. Backend는 요청 말끝의 제한적 정규화와 제외 표현 구두점 처리를 보완했다. 수정 후 같은 문항을 실행하면 이미 진단에 사용한 회귀이며 최초 봉인 정확도를 다시 쓰지 않는다.

최초 평가는 기존 MLflow 실험 33의 [질문군 평가 run](https://mlflow.dove-nest.com/#/experiments/33/runs/f2a5a01888cb428fa9db8d056e4f9bfd)에 기록했다. 근거는 `docs/verification/assets/2026-10-24-question-family-routing/mlflow-evaluation.json`이다. 첫 현재 이미지 `f0ad3464836b`는 최종 보완 후보 이미지와 구분한다. 독립 backend 검사 근거는 같은 폴더의 `backend-independent.log`다.

### 첫 피드백 노출 회귀의 추가 실패와 보완

이미지 `107dc70094d3`의 첫 24문항 회귀는 22/24·6/8군이었다. 최초 봉인 평가 뒤 이미 진단에 사용한 문항이므로 새로운 holdout 점수가 아니다. 이 시도는 `regression-attempt1/`의 응답·점수·배포 영수증으로 보존했다.

- H05B: 모델 unresolved에 마침표를 포함한 “궁금해.”가 남았다. 요청 말끝 문법 확인 때에만 마지막 `.!?`를 제외하고, 원문 근거 전체 일치 검증은 유지하도록 보완했다.
- H06C: 원문 “쇠백로와…”와 달리 모델 관계 근거가 “과 같은 먹이 생태 범주인”이었다. 정확히 인접한 기준 종·원래 조사·나머지 원문이 모두 유일하게 맞을 때만 `reference_particle`로 복구하고 기존 `_build`와 실제 감사는 계속 통과해야 한다.

추가 독립 검사는 문장부호 2 methods·조사 3 methods 통과였다. 모델 감사 false를 승인으로 바꾸거나 일반적인 임의 의역을 허용하지 않는다. 마지막 실제 24문항은 이 실패를 보고 보완한 두 번째 피드백 노출 회귀로 별도 기록했다.

### 최종 피드백 노출 회귀

`regression-score.json`에서 24/24문항·8/8질문군이 판정 기준을 통과했다. 동일 요청의 실제 API·trace를 평가했고 모델·서버 응답을 모의하지 않았다. 독립 재채점은 같은 점수 JSON과 HTTP 200인 고유 trace 24개를 확인했으며 `final-independent-signoff.json`에 기록했다. 최초 봉인 16/18·4/6군과 첫 회귀 22/24·6/8군은 수정하지 않고 보존했다.

| 최종 응답 분류 | 건수 | 해석 |
| --- | --- | --- |
| `supported_answer` | 19 | 지원 조건으로 답변 |
| `unsupported_specific_food` | 1 | 특정 식물 먹이 자료를 일반 먹이로 완화하지 않음 |
| `supported_no_matching_results` | 1 | 지원 조건으로 실행했으나 일치 결과 없음 |
| `negated_condition` | 1 | 부정 조건 보류 |
| `supported_source_no_data` | 2 | H05A·H05B 동일 아종의 직접 자료 없음, 부모 종 대체 금지 |

따라서 24/24는 모든 질문에 종 목록을 답했다는 뜻이 아니다. 질문군의 동치·대조 및 안전한 보류까지 포함한 판정 통과다. 직접 자료 부족 두 문항을 답변 성공으로 바꾸거나 현재 자료가 있다고 주장하지 않는다.

최종 실제 H05B trace에서는 `terminal_request`의 before가 `["궁금해"]`인 보정을 관측했다. 구두점이 포함된 말끝 및 잘못된 조사 복구는 결정론 검사 근거가 있다. 최종 H06C 모델은 원래 올바른 조사를 생성했으므로 최종 실제 요청에서 `reference_particle` 보정 분기가 실행됐다고 주장하지 않는다.

최종 평가는 기존 MLflow 실험 33의 [최종 질문군 회귀 run](https://mlflow.dove-nest.com/#/experiments/33/runs/6e2950e57da947c9a2ced441eb76dae3)에 FINISHED로 기록하고 artifacts를 재조회했다. 이전 22/24 회귀 자료도 함께 보존했다. 첫 평가 run도 유지했으며, 두 run을 최초 미노출 성능 하나로 합치지 않는다.

원본 봉인 자료는 그대로 유지하고 후속은 `implementation_feedback_exposed: true` 회귀로 기록했다. 이번 성과가 사람 검토된 정답셋·새 독립 일반화 점수·모델 확률적 안정성 검증을 뜻하지 않는다. UI 변경이 없어 이번 Node 전체·브라우저·물리 모바일 검증은 재실행하지 않았다.

### 질문군과 평가 분리

공개 tuning은 2개 군·6문항(지원 5·보류 1), 봉인 holdout은 6개 군·18문항(지원 17·보류 1)이다. 각 군의 동치 두 문항이 개별적으로 통과하고 실행 계획도 일치해야 하며, 대조 문항은 별도 예상 조건이나 보류를 만족하고 동치 계획에 합쳐지지 않아야 군 전체 통과다.

계급 범위는 목·과·속·종·아종이고 동치와 대조는 서식지 값·수치 비교·분류 범위·부정·종/아종·기준 종을 포함한다. 정확한 예상 계획 signature를 split 사이에 분리했지만 어휘와 과제 유형은 의도적으로 겹친다. 새로운 도메인으로의 일반화를 검증한 설계는 아니다.

자료 검증에서 24문항의 계약·catalog identity·분리 기준을 확인했고 기존 문항 exact 중복 0·split 간 예상 signature 중복 0을 기록했다. 이는 실제 파서나 봉인 질문 실행 결과가 아니다. 평가 자료는 독립 모델이 작성했고 사람 검토는 없었다. 최초 봉인 평가와 이후 진단·재실행을 반드시 분리한다.


첫 실패와 보완 후 회귀는 별도로 보존한다. 피드백을 본 문항의 재검증을 독립 미노출 평가로 집계하지 않는다. 조건이 맞았더라도 이름 해소나 자료 조회 실패로 답변하지 못한 경우를 지원 성공으로 승격하지 않는다.
