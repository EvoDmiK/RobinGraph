# RG-301 채팅 플로우 지연 점검 — 2026-10-08

## 요청 배경·목표

Jev 의도 분류가 약 1.8초이고 전체 채팅이 7~9초라는 이전 검증을 바탕으로, 사용자가 플로우 시간 점검을 요청했다. NAS TEST 공개 API 실측과 실제 MLflow trace를 대조하여 의도 분석 외 병목을 확인한다. 기능 개선이나 재배포를 이번 작업에 포함하지 않는다.

## 검증 범위와 방법

루트 환경 파일에서 MLflow 추적 주소·실험 이름만 읽어 `robingraph-test`의 기존 trace를 조회했다. NAS TEST 공개 API에서 청둥오리를 대상으로 5개 경로를 각 2회씩 순차 실행했다. 채팅 자동 아종 질문, 명시적 profile 채팅, 직접 아종 API를 먼저 반복하고 직접 profile·similar API를 추가 비교했다. 총 HTTP 10회이며 자동 아종 질문 2회에 실제 Jev 호출이 발생했다. 코드·환경 파일·DB 적재 데이터·배포는 변경하지 않았다.

실제 DB/API/SDK 기록을 사용했으며 응답 모의 주입은 없다. 캐시를 지우거나 컨테이너를 재시작하지 않았다. 따라서 이번 반복 결과를 콜드 스타트 결과라고 표현하지 않는다. 클라이언트 시간은 HTTP 요청 시작부터 JSON 수신·파싱까지이고 root span은 애플리케이션 함수 범위이므로 동일한 시간이 아니다.

## 실제 재측정 결과

| 경로 | 1회차 HTTP | 2회차 HTTP | 확인한 내용 |
| --- | ---: | ---: | --- |
| 자동 아종 채팅: 청둥오리 아종 알려줘 | 3,310ms | 3,060ms | Jev 호출 포함, 두 번 모두 answer |
| 명시적 종 정보 채팅: intent=profile | 3,106ms | 2,781ms | Jev 호출 없음, 두 번 모두 answer |
| 직접 아종 목록 API | 340ms | 597ms | 실제 목록 조회 |
| 직접 종 프로필 API | 806ms | 575ms | 기본 카드만 조회 |
| 직접 비슷한 새 API | 2,580ms | 2,556ms | 추천 생성 자체의 지연을 확인 |

이번 자동 아종 채팅의 실제 Jev span은 2,278/1,976ms, 프로필 RunnableSequence는 197/260ms였다. 종 해소는 93/92ms, 특성 조회는 81/131ms였다. 사진·설명 단계는 대부분 수 ms~수십 ms였다. 기존 코드의 시간 단위 메모리 캐시와 부합하지만 캐시 hit 메트릭은 없어 적중을 직접 증명한 수치는 아니다.

명시적 profile 채팅의 프로필 RunnableSequence는 223/221ms였다. 그런데 root span은 2,702/2,489ms였고, 프로필 흐름 뒤에 약 2초 이상의 직접 child span으로 계측되지 않은 구간이 있었다. 소스에서 일반 profile 응답은 프로필 구성 **후** `similar_species_handler(name)`을 동기 실행하는 것을 확인했다. 별도 추천 API도 2.56~2.58초여서 해당 단계가 추가 지연의 유력한 원인이다. 추천 내부 DB 쿼리·계통 계산·정렬 각각의 시간까지 단정하지 않는다.

## 기존 느린 trace의 원인

기존 청둥오리 아종 질문의 느린 trace 2개를 재조회했다.

| 구간 | trace A | trace B |
| --- | ---: | ---: |
| 애플리케이션 root 전체 | 7,822ms | 7,971ms |
| Jev 의도 분석 | 1,975ms | 2,293ms |
| 프로필 흐름 전체 | 5,605ms | 5,302ms |
| 사진 조회 image_stage | 1,858ms | 2,257ms |
| 설명 notes_stage | 5,419ms | 5,101ms |
| 설명 내부 Gemini Models.generate_content | 2,892ms | 3,001ms |
| 종 해소 resolve_species | 112ms | 148ms |
| 특성 trait_stage | 103ms | 128ms |

trace A는 `tr-2ad6941aba7713f857330090053bac5d`, B는 `tr-45494841a163e757627288b65cd3ab0c`이다. 사진·설명·특성 등은 `RunnableParallel`에서 동시에 실행되므로 시간을 합산하지 않는다. Gemini span도 notes_stage 안에 포함된다. 설명 자료를 Wikidata/Wikipedia에서 수집하고 Gemini로 요약하는 경로가 약 5초의 병목이며, Jev와 직렬로 이어져 전체가 약 8초가 됐다. 기존 설명·사진 캐시는 프로세스 내부 시간 단위 캐시다. 미적중·프로세스 재시작·시간 구간 변경 시 다시 외부 작업이 필요할 수 있다. 특정 기존 요청의 정확한 캐시 미적중 원인은 직접 확인하지 않았다.

아종 질문도 현재 `species_profile_handler`로 사진·설명을 포함한 전체 부모 종 카드를 먼저 만들고, 그 다음 `subspecies_handler`를 실행한다. 따라서 아종 목록만 필요한 질문도 부모 카드의 느린 외부 설명을 기다릴 수 있다. 단순 DB 종 해소·특성 조회만으로 전체 7~9초를 설명할 수 없으며, 이전 안내의 ‘DB 조회와 후속 처리’는 외부 사진·설명·추천의 영향을 더 명확히 구분해야 한다.

## 개선 권장 순서와 변경 전후 목표

1. **필수 답변과 부가 자료 분리**: 현재 아종 목록 응답이 전체 부모 카드의 사진·설명까지 기다린다. 아종 목록·부모 식별자·분류판 검증을 먼저 제공하고 사진·설명은 후속 조회로 표시하는 방향을 우선 검토한다. 일반 profile도 비슷한 새 추천을 후속 조회로 분리하면 약 2초대 추가 대기를 줄일 여지가 있다. 실제 절감량은 구현 후 재측정해야 한다.
2. **계측 보완**: 이름 관계 조회·아종 목록·비슷한 새 추천에 별도 span을 추가한다. 추천 내부 후보 조회·계통 계산·정렬도 나눠야 DB 비용과 CPU 비용을 구분할 수 있다. 기존 root 밖 HTTP 차이를 네트워크나 MLflow export 하나의 비용으로 단정하지 않는다.
3. **Jev 호출 감소**: 자주 쓰는 명확한 표현의 결정 규칙과 안전한 의도 결과 캐시를 검토한다. 라우터 설정·모델·프롬프트 변경 시 캐시 무효화가 필요하다. 종·분류 데이터 결과의 활성 분류판 검증을 생략하는 캐시는 권장하지 않는다.
4. **기존 외부 자료 캐시 운영 검토**: 이미 있는 시간 단위 캐시의 적중·미적중을 관측한 뒤 TTL·사전 수집·영속화 필요성을 결정한다. 캐시가 없다는 전제로 중복 구현하지 않는다.

## 변경 파일·검증·커밋·배포·한계

변경 파일은 이 작업 문서와 [지연 검증 JSON](assets/2026-10-08-RG013-flow-latency.json)이다. Obsidian에도 동일한 핵심 수치·검증 범위·한계를 기록한다. 기능 코드 변경이 없으므로 회귀 테스트 600개를 재실행하지 않았고, 이전 600개 통과 결과를 이번 점검에서 다시 실행한 것처럼 세지 않는다. 이번에는 실제 HTTP 10회와 MLflow 기록 대조를 수행했다. 모두 HTTP 정상 응답이며 채팅 4회는 answer 판정이다. 문서·증거를 dev에 별도 커밋한다. 배포는 수행하지 않았으며 NAS TEST는 기존 구현 버전을 사용한다.

각 경로 2회 측정은 부하 시험이나 p95 추정이 아니다. 시간대·캐시·외부 제공자 상태·동시 요청에 따라 결과가 달라질 수 있다. 이번 작업은 병목 확인까지이며 자동/지연 로딩 UI, 추가 span, 추천 최적화, Jev LangChain 연결은 아직 구현하지 않았다. 인증 정보는 기록하지 않는다.
